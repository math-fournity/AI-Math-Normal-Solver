## 2. 方案

### 2.1 总体思路

1. 用AQL从ArangoDB查出3,448个problem_key（2,565从未处理 + 639检测误判 + 244基础设施失败）
2. 清空Redis的pending/failed/completed队列（running已经是0）
3. 把3,448个problem_key全部入队到math:pending
4. 更新ArangoDB中这3,448题的extraction_status为'queued'
5. 验证math:pending数量=3,448
6. 启动系统时**不启动feeder**，只启动runner/collector/reporter/retry/monitor

### 2.2 为什么不启动feeder

feeder的工作方式是：查ArangoDB中`extraction_status == 'pending'`的题，入队后更新为'queued'。如果启动feeder：
- feeder会查到901+28+639=1,568个`extraction_status == 'pending'`的题并入队（这些是3,448的子集）
- 但feeder**不会**查到extraction_status为queued/completed/failed的题（1,880题）
- 所以feeder无法把3,448题全部入队

因此必须用专门的脚本一次性入队，之后不启动feeder。

### 2.3 为什么244 infra失败题需要特殊处理

retry服务通过查`devin_problem_runs`中infra失败记录数来判断是否达到max_retries（默认3）。这244题已有3+次infra失败记录，如果再次infra失败，retry（默认max_retries=3）不会重试它们。

**解决方案**：启动retry时用`--max-retries 6`，给这244题额外3次重试机会。

## 3. 执行步骤

### 步骤1：写队列准备脚本

新建 `xishujuzhen/solver_harness/pipe/scripts/prepare_final_queue.py`：

功能：
1. 从ArangoDB查出3,448个problem_key（2,565从未处理 + 639检测误判 + 244 infra失败）
2. 支持 `--dry-run` 只查数量不入队
3. 清空Redis的pending/failed/completed队列
4. 把3,448个problem_key入队到math:pending（score=priority，全部=1）
5. 更新ArangoDB中这3,448题的extraction_status为'queued'
6. 打印验证结果

AQL查询逻辑：

```aql
// 从未处理过的题
FOR p IN problem_extraction_progress
  FILTER p.difficulty_tier == 1
  LET has_run = (
    FOR r IN devin_problem_runs
      FILTER r.problem_id == p._key
      FILTER r.batch_id == "pipe-runner"
      LIMIT 1
      RETURN 1
  )
  FILTER LENGTH(has_run) == 0
  RETURN {key: p._key, priority: p.priority}

// 检测误判题（answer_leak/answer_leak_in_input，检测已取消）+ infra失败题
// 两类合并查询：按每题最后run的status判断
FOR p IN problem_extraction_progress
  FILTER p.difficulty_tier == 1
  LET last_run = (
    FOR r IN devin_problem_runs
      FILTER r.problem_id == p._key
      FILTER r.batch_id == "pipe-runner"
      FILTER r.status != "running"
      SORT r.ended_at DESC
      LIMIT 1
      RETURN r.status
  )
  FILTER LENGTH(last_run) > 0
  FILTER last_run[0] IN [
    "answer_leak", "answer_leak_in_input",               // 检测误判（已取消）
    "rate_limited", "dead_session", "crash_recovered",   // 基础设施失败
    "failed_connection", "launch_error"
  ]
  RETURN {key: p._key, priority: p.priority || 1}
```

## 4. 注意事项

### 4.1 清空failed/completed队列的影响

清空math:failed和math:completed会丢失历史记录。但这些队列只是Redis中的临时缓冲，真正的结果数据在ArangoDB的devin_problem_runs中，不会丢失。reporter的统计基于ArangoDB而非Redis队列。

### 4.2 244 infra失败题的retry限制

这244题在devin_problem_runs中已有3+次infra失败记录。启动retry时必须用`--max-retries 6`，否则这些题如果再次infra失败将不会被重试。

### 4.3 队列处理完成后

当math:pending降到0且math:running也降到0时，平凡解题系统的工作完成。此时：
- tier=1的平凡解题系统处理范围已全部覆盖
- 剩余未解决题（token_limit等）交给其他系统
- 可以停止所有服务

### 4.4 不入队的题

以下题**不在这个队列中**，也不应该被加入：

| 类别 | 数量 | 不入队原因 | 去向 |
|---|---|---|---|
| token_limit | 9,336 | 需要更大token预算，在固定token预算下重试结果不变 | 交给其他系统处理 |
| ai_gave_up | 498 | AI主动输出`### I CANNOT SOLVE THIS`，认为解不了，重试大概率同样结果 | 交给其他系统处理 |
| 卡住/空转/无proof | 235 | 边缘case（failed_stall/failed_thinking_spin/failed_no_proof），重试大概率同样行为 | 不处理，是Profile数据 |

> **注**：639题"数据问题（题目含答案/答案泄漏）"原在此列表中，但调查发现原始数据本身就包含答案（不是提取bug），泄漏检测已取消，这639题已纳入入队范围（见§1.2）。
