# 平凡解题系统队列准备方案

> **创建日期**：2026-08-21
> **目标**：一次性把平凡解题系统需要处理的2,809题全部入队到Redis，之后feeder不需要再查ArangoDB选题，队列自包含。
> **背景**：见 `dev-docs/402-v0-2026-08-21-tier1做题结果调查报告.md` 第5节——平凡解题系统只负责2,809题（2,565从未处理 + 244基础设施失败），token_limit等题不在处理范围内。

---

## 1. 现状

### 1.1 Redis当前状态

| 队列 | 数量 | 说明 |
|---|---|---|
| math:pending | 992 | 系统停止后残留的未处理题（全部tier=1） |
| math:running | 0 | 无运行中的题 |
| math:failed | 11,211 | 历史失败记录（retry已处理过） |
| math:completed | 26,581 | 历史完成记录 |

### 1.2 2,809题的extraction_status分布

**从未处理过的2,565题**（全部priority=1）：

| extraction_status | 数量 | 说明 |
|---|---|---|
| queued | 1,212 | feeder曾入队但runner未处理（如断电丢失） |
| pending | 901 | feeder从未选中 |
| completed | 452 | extraction_status标记为completed但无run记录（可能是旧系统标记） |

**244基础设施失败题**：

| extraction_status | 数量 | 说明 |
|---|---|---|
| queued | 175 | 最后一次入队后标记 |
| completed | 33 | extraction_status标记为completed但最后run是infra失败 |
| pending | 28 | retry曾重置为pending |
| failed | 8 | extraction_status标记为failed |

### 1.3 关键发现

- 2,565题全部priority=1，入队时score统一
- extraction_status分布杂乱（queued/pending/completed/failed都有），不能依赖这个字段判断题是否该入队
- 正确的判断标准是：**devin_problem_runs中是否有该题的run记录**（从未处理）或**最后run的status**（infra失败）

## 2. 方案

### 2.1 总体思路

1. 用AQL从ArangoDB查出2,809个problem_key
2. 清空Redis的pending/failed/completed队列（running已经是0）
3. 把2,809个problem_key全部入队到math:pending
4. 更新ArangoDB中这2,809题的extraction_status为'queued'
5. 验证math:pending数量=2,809
6. 启动系统时**不启动feeder**，只启动runner/collector/reporter/retry/monitor

### 2.2 为什么不启动feeder

feeder的工作方式是：查ArangoDB中`extraction_status == 'pending'`的题，入队后更新为'queued'。如果启动feeder：
- feeder会查到901+28=929个`extraction_status == 'pending'`的题并入队（这些是2,809的子集）
- 但feeder**不会**查到extraction_status为queued/completed/failed的题（1,880题）
- 所以feeder无法把2,809题全部入队

因此必须用专门的脚本一次性入队，之后不启动feeder。

### 2.3 为什么244 infra失败题需要特殊处理

retry服务通过查`devin_problem_runs`中infra失败记录数来判断是否达到max_retries（默认3）。这244题已有3+次infra失败记录，如果再次infra失败，retry（默认max_retries=3）不会重试它们。

**解决方案**：启动retry时用`--max-retries 6`，给这244题额外3次重试机会。

## 3. 执行步骤

### 步骤1：写队列准备脚本

新建 `xishujuzhen/solver_harness/pipe/scripts/prepare_final_queue.py`：

功能：
1. 从ArangoDB查出2,809个problem_key（2,565从未处理 + 244 infra失败）
2. 支持 `--dry-run` 只查数量不入队
3. 清空Redis的pending/failed/completed队列
4. 把2,809个problem_key入队到math:pending（score=priority，全部=1）
5. 更新ArangoDB中这2,809题的extraction_status为'queued'
6. 打印验证结果

AQL查询逻辑：

```aql
// 从未处理过的题
FOR p IN problem_extraction_progress
  FILTER p.difficulty_tier == 1
  LET has_run = (
    FOR r IN devin_problem_runs
      FILTER r.problem_id == p._key
      FILTER r.batch_id == "pipe-runner"
      LIMIT 1
      RETURN 1
  )
  FILTER LENGTH(has_run) == 0
  RETURN {key: p._key, priority: p.priority}

// infra失败的题（按每题最后run）
FOR p IN problem_extraction_progress
  FILTER p.difficulty_tier == 1
  FOR r IN devin_problem_runs
    FILTER r.problem_id == p._key
    FILTER r.batch_id == "pipe-runner"
    FILTER r.status != "running"
    SORT r.problem_id, r.ended_at DESC
    COLLECT problem_id = r.problem_id INTO runs = r.status
    LET last_status = runs[0]
    FILTER last_status IN ["rate_limited","dead_session","crash_recovered","failed_connection","launch_error"]
    RETURN {key: problem_id, priority: 1}
```

### 步骤2：dry-run验证


验证输出：
- 从未处理过的题：2,565

- 合计：2,809

### 步骤3：执行入队

执行后验证：

## 4. 注意事项

### 4.1 清空failed/completed队列的影响

清空math:failed和math:completed会丢失历史记录。但这些队列只是Redis中的临时缓冲，真正的结果数据在ArangoDB的devin_problem_runs中，不会丢失。reporter的统计基于ArangoDB而非Redis队列。

### 4.2 244 infra失败题的retry限制

这244题在devin_problem_runs中已有3+次infra失败记录。启动retry时必须用`--max-retries 6`，否则这些题如果再次infra失败将不会被重试。

### 4.3 队列处理完成后

当math:pending降到0且math:running也降到0时，平凡解题系统的工作完成。此时：
- tier=1的平凡解题系统处理范围已全部覆盖
- 剩余未解决题（token_limit等）交给其他系统
- 可以停止所有服务

### 4.4 不入队的题

以下题**不在这个队列中**，也不应该被加入：

| 类别 | 数量 | 不入队原因 |
|---|---|---|
| token_limit | 9,336 | 需要更大token预算，交给其他系统 |
| AI主动放弃/卡住/空转/无proof | 733 | 是Profile数据，重试结果不变 |
| 数据问题（题目含答案/答案泄漏） | 639 | 题目本身有问题 |
