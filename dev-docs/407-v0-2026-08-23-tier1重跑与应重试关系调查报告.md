## 1. 调查背景

1. 1,175题重跑前是什么状态？重跑后变成了什么？

## 2. 调查方法

### 2.1 使用的数据源

| 数据源 | 用途 |
|---|---|
| ArangoDB `problem_extraction_progress` | tier=1题目总数、extraction_status、source_dataset |
| ArangoDB `devin_problem_runs` | 所有pipe-runner batch的run记录，按problem_id取最后一条终态run |
| Redis `math:completed` + `math:failed` | 队列中的verdict分布，检测empty_problem_text |

### 2.2 关键方法

1. **按problem_id取最后一条终态run**：一道题可能有多条run记录（重试时），只看最后一条的status作为该题的"当前状态"。
2. **重跑名单定义**：指定时间（`2026-08-22T09:00:00Z`）后所有pipe-runner run涉及的unique problem_id集合。
3. **重跑前status**：同一批题在指定时间之前的最后一条终态run的status。
4. **交叉分析**：将重跑名单与"应重试"池（从未处理 + 基础设施失败）做集合运算，看两个集合是否重叠。

## 4. 完整答案

### 4.1 为什么769题成功但"应重试"池还有607题？

**因为1,175题重跑和607题"应重试"是两个几乎不相交的集合：**

```
1,175题重跑池（AI能力失败）        607题"应重试"池
┌──────────────────────┐          ┌──────────────────────┐
│ failed_token_limit   │          │ 从未处理 452题       │
│ 1,111题（误分类）    │          │ （empty_problem_text）│
│                      │          │  ← 数据问题，无关     │
│ failed_no_proof      │          ├──────────────────────┤
│ 64题                 │          │ 基础设施失败 155题    │
│                      │          │  其中23题 ← 重跑后    │
│ 重跑后：             │          │  仍失败的（交集=23）  │
│ 769题→solved         │          │  132题 ← 之前批次遗留 │
│ 376题→仍token_limit  │          │                      │
│ 23题→基础设施失败──────┼──────────┼→ 这23题加入了应重试池│
│ 7题→其他             │          │                      │
└──────────────────────┘          └──────────────────────┘

两个集合的交集 = 23题（重跑后变成基础设施失败的）
```

- 1,175题重跑前是 **AI能力失败**（failed_token_limit/failed_no_proof），不在"应重试"池中
- 769题成功 → 从"AI能力失败"池移出，进入"已解决"——但这不影响"应重试"池的数字
- 23题重跑后变成基础设施失败 → 从"AI能力失败"池转入"应重试"池（反而让"应重试"池+23）
- 607题"应重试"池中：452题是empty_problem_text（数据问题），132题是之前批次遗留的基础设施失败

### 4.2 真正需要重跑的题

| 类别 | 数量 | 是否需要重跑 | 原因 |
|---|---|---|---|
| 基础设施失败 | 155 | **是** | retry已重试6次仍失败，需排查系统性问题后重跑 |
| 从未处理（empty_problem_text） | 452 | **否** | 题目文本为空，是数据问题，需修复题目数据而非重跑 |
| **真正需要重跑** | **155** | — | — |

### 4.3 452题empty_problem_text的处理建议

这452题需要从原始parquet文件重新提取`problem_text`，而不是重新入队重跑。涉及4个数据集：

| source_dataset | 数量 | 处理建议 |
|---|---|---|
| omni_math | 173 | 检查原始parquet的question字段是否为空 |
| compfiles | 157 | 检查原始parquet的question字段是否为空 |
| fate | 115 | 检查原始parquet的question字段是否为空 |
| matharena | 7 | 检查原始parquet的question字段是否为空 |

如果原始parquet中question字段也为空，说明这些题本身就是空题，应该从题库中标记为`skipped`（skip_reason=empty_problem_text），不再尝试。

## 5. 认知更新

### 5.1 check_tier1_remaining.py的误导性

`check_tier1_remaining.py`将452题"从未处理"归入"应重试"池，但没有检测这些题是empty_problem_text。这导致"应重试"池的数字（607）被高估——真正需要重跑的只有155题。

**建议**：`check_tier1_remaining.py`应增加empty_problem_text检测，将empty_problem_text题从"应重试"池中排除。

### 5.2 两个视角的互补关系

| 脚本 | 视角 | 看到什么 | 看不到什么 |
|---|---|---|---|
| check_tier1_remaining.py | DB视角 | DB run记录的status分类 | empty_problem_text（无run记录） |
| check_tier1_retention.py | 硬盘视角 | candidate_solved的文件完整性 | empty_problem_text（无目录） |
| **analyze_rerun_vs_remaining.py** | **交叉视角** | **重跑名单vs应重试池的关系 + empty_problem_text检测** | — |

本次调查新增的`analyze_rerun_vs_remaining.py`填补了前两个脚本的盲区：它能检测出"从未处理"题中哪些是empty_problem_text（数据问题），哪些是真正没跑过的题。

### 5.3 "769题成功"的正确理解

769题成功意味着：1,175题中769题从AI能力失败变成了已解决。这是一个**独立的成果**——它解决的是"被误分类的AI能力失败题"，不是"应重试"池中的题。

"应重试"池的变化只有：+23题（重跑后变成基础设施失败的），-0题（重跑没有解决任何"应重试"池中的题，因为两个集合几乎不相交）。
