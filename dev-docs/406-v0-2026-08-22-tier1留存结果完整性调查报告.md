## 7. 排查结果：failed_token_limit无export的1,111题

### 7.1 根因

**这1,111题不是真正的token_limit失败，而是API连接错误被collector误分类为failed_token_limit。**

pane_snapshot内容全部是：
```
Error: Agent error: Connection error, send a message to continue retrying: {
  "cognition.ai/errorKind": "unavailable",
  "cognition.ai/retryable": true
}
DEVIN_CLI_EXITED code=1
```

devin cli遇到API连接错误后退出（code=1），没有产生export。collector看到`DEVIN_CLI_EXITED`后判定终态，但误分类为`failed_token_limit`而非`failed_connection`/`dead_session`。

### 7.2 数据证据

| 指标 | 无export（1,111题） | 有export（8,933题） |
|---|---|---|
| 占failed_token_limit比例 | 11% | 89% |
| 其他文件 | si+pane+tmux全有（只缺export） | 全有 |
| runtime中位数 | 554s | 360s |
| runtime平均值 | 446s | 386s |
| pane内容 | Connection error + DEVIN_CLI_EXITED code=1 | 正常推理过程 + token用完 |

### 7.3 时间分布

全部集中在2026-08-13 04:21-04:30（约10分钟的连接错误风暴）。这是API服务短暂不可用导致的批量失败。

### 7.4 数据集分布

| 数据集 | 无export / 总数 | 比例 |
|---|---|---|
| polymath | 745 / 4,961 | 15% |
| deepmath_103k | 361 / 2,043 | 17% |
| oda_math_460k | 5 / 1,340 | 0% |

### 7.5 性质判定

- **不是token_limit失败**——真正的token_limit失败有完整export（推理链被截断但devin cli正常退出并写了export）
- **是基础设施失败**——API连接错误属于基础设施失败，应该被分类为`failed_connection`或`dead_session`
- **应该被重试**——基础设施失败应该由retry自动重试，但因为被误分类为`failed_token_limit`（模型能力失败），没有被重试
- **export缺失是正常的**——devin cli遇到连接错误后直接退出（code=1），没有产生export，这不是落盘bug

### 7.6 影响

- 这1,111题的thinking数据丢失——因为devin cli根本没开始推理就遇到了连接错误
- 这1,111题被错误地归入"需要另外一套系统处理"的10,069题中——实际上它们应该被重新跑
- collector的分类逻辑有bug——连接错误+DEVIN_CLI_EXITED code=1应该分类为基础设施失败，不是failed_token_limit

### 7.7 根因详解：为什么没有重试

**collector分类顺序的bug**：

`collector.py`中`classify_termination`函数的检查顺序是：
1. proof检测 → candidate_solved
2. **TOKEN_LIMIT_PATTERNS**（第379行）→ failed_token_limit
3. RATE_LIMIT_PATTERNS → rate_limited
4. 超时 → failed_timeout
5. session结束时：RATE_LIMIT → **TOKEN_LIMIT** → CONNECTION_PATTERNS

而`TOKEN_LIMIT_PATTERNS`中有`"Send a message to continue"`，连接错误的pane内容是：
```
Error: Agent error: Connection error, send a message to continue retrying: {
  "cognition.ai/errorKind": "unavailable",
  "cognition.ai/retryable": true
}
```

pane中的`"send a message to continue retrying"`包含`"send a message to continue"`子串，被`TOKEN_LIMIT_PATTERNS`先匹配，返回`failed_token_limit`。

`CONNECTION_PATTERNS`（含`"connection error"`）的检查在`TOKEN_LIMIT_PATTERNS`之后，永远执行不到。

**retry系统没有问题**——`retry_infrastructure.py`的`INFRA_FAILURES`已经包含`failed_connection`，只要collector正确分类，retry就会自动重试。问题在collector的分类顺序导致连接错误被误分类为`failed_token_limit`（模型能力失败），retry不会重试模型能力失败。

### 7.8 修复

已修复`collector.py`的分类顺序——`CONNECTION_PATTERNS`检查移到`TOKEN_LIMIT_PATTERNS`之前：

**session还在运行时**（§3.5-3.7）：
- 旧顺序：TOKEN_LIMIT → RATE_LIMIT
- 新顺序：CONNECTION → TOKEN_LIMIT → RATE_LIMIT

**session已结束时**（§5）：
- 旧顺序：RATE_LIMIT → TOKEN_LIMIT → CONNECTION
- 新顺序：CONNECTION → RATE_LIMIT → TOKEN_LIMIT

修复后，连接错误会被正确分类为`failed_connection`，retry会自动重试。
