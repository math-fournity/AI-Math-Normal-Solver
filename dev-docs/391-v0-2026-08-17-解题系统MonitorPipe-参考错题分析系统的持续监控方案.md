# 391号：解题系统Monitor Pipe——参考错题分析系统的持续监控方案

**日期**：2026-08-17
**背景**：解题系统（pipe/5服务）之前没有Monitor Pipe，只有`pipe_control.py health`一次性检查。参考错题分析系统的`monitor_pipe.py`+`monitor_check.sh`架构，为解题系统增加持续监控能力。

---

## 1. 设计动机

### 1.1 解题系统已知问题

解题系统在长期运行中反复出现以下问题，需要持续监控：

1. **rate limit**——50并发触发API限流（2026-08-14教训），安全上限是30并发
2. **僵尸session**——devin cli退出后tmux session残留，pane空白但tmux_running=True
3. **export_missing**——completed的题没有export文件（基础设施问题）
4. **solve_time > runtime**——solve_time可信度问题（extract_solve_time.py逻辑bug）
5. **throughput下降**——从600题/时降到12题/时（并发=1假活状态）

### 1.2 错题分析系统的Monitor Pipe经验

错题分析系统已有成熟的Monitor Pipe架构（`analysis-devin-failure-system/src/monitor_pipe.py`）：

- **持续运行**：每5分钟一轮，7类自动检查 + AI review抽样
- **alert机制**：检查发现问题→写alert到ArangoDB的`monitor_alerts`集合
- **标准化检查脚本**：`monitor_check.sh`输出4项检查 + 每项后附"需要检查"提示
- **AI review抽样**：每3轮抽样2条审计结果，标记为needs_ai_review

### 1.3 --prompt-file使用经验

错题分析系统的`selection_launcher.py`用`devin -p --prompt-file {agents_md_path}`直接注入大prompt文件：

```python
devin_cmd = (
    f"devin -p "
    f"--prompt-file {agents_md_path} "
    f"--model {DEVIN_MODEL} "
    f"--respect-workspace-trust false "
    f"--permission-mode {DEVIN_PERMISSION_MODE} "
    f"--export {export_path}; "
    f"echo DEVIN_CLI_EXITED code=$?; "
    f"sleep 999999"
)
```

**优势**（记录在全局AGENTS.md中）：
- 避免read工具调用（0 tool_calls，10秒内输出完整XML）
- 避免shell转义问题（题目文本中有特殊字符时`-p '{prompt}'`会出错）
- 适用于prompt文件>15KB且内容自洽的场景

**解题系统当前状态**：`solver_harness.py`第608行用`devin -p '{prompt}'`内联prompt，**没有用--prompt-file**。这是未来可改进的点——但当前题目prompt较小（AGENTS.md模板+problem_text），内联模式可用。

## 2. 实现方案

### 2.1 新增文件

| 文件 | 用途 |
|---|---|
| `xishujuzhen/solver_harness/pipe/monitor_pipe.py` | Monitor Pipe主程序（持续监控+alert+AI review抽样） |
| `xishujuzhen/solver_harness/pipe/scripts/monitor_check.sh` | 标准化检查脚本（5项检查+对AI的提醒） |

### 2.2 修改文件

| 文件 | 修改内容 |
|---|---|
| `xishujuzhen/solver_harness/pipe/pipe_control.py` | 新增`monitor`子命令（start/stop/status）+ start默认启动Monitor Pipe + stop停止Monitor Pipe |
| `xishujuzhen/solver_harness/pipe/pipe_start.sh` | 新增第5步启动Monitor Pipe（6步流程） |
| `xishujuzhen/solver_harness/pipe/pipe_stop.sh` | 停止时包含pipe-monitor session |

### 2.3 Monitor Pipe的8项自动检查

| 检查项 | alert_type | severity | 阈值 | 说明 |
|---|---|---|---|---|
| A. session_health | session_health | critical | — | harness-p=0但Redis running>0或pending>0 |
| B. queue_progress | queue_stalled/no_completions | critical/warning | 15分钟无变化 | pending没变或completed没增加 |
| C. rate_limit_detection | rate_limit | critical/warning | ≥3个critical, >0个warning | 最近interval内rate_limited数量 |
| D. zombie_sessions | zombie_sessions | warning | ≥2个 | 空pane僵尸session |
| E. export_landing | export_missing | critical | 缺失率>10% | completed的题无export文件 |
| F. solve_time_credibility | solve_time_anomaly | warning | >10% | solve_time > runtime |
| G. failure_rate | failure_rate | warning | >15% | 最近interval失败率 |
| H. throughput_trend | throughput_drop | warning | 下降>50% | 对比前后轮次吞吐 |

### 2.4 AI review抽样

- **频率**：每3轮（约15分钟）抽样2条candidate_solved
- **标记**：DB中`ai_reviewed=flagged`，避免重复抽样
- **alert**：创建`ai_review_sample` info级alert，包含proof_snippet
- **AI职责**：检查proof的数学正确性、是否有幻觉、是否答案泄漏

### 2.5 alert集合

- **集合名**：`pipe_monitor_alerts`（避免与错题分析系统的`monitor_alerts`冲突）
- **alert结构**：
  ```json
  {
    "_key": "pmon-{timestamp}-{type}",
    "alert_type": "session_health | rate_limit | ...",
    "severity": "critical | warning | info",
    "details": {"summary": "...", ...},
    "status": "new | reviewing | fixed | wontfix",
    "created_at": "ISO timestamp",
    "resolved_at": null
  }
  ```

## 3. 检查脚本设计（monitor_check.sh）

### 3.1 5项检查

| 检查项 | 内容 | 数据来源 |
|---|---|---|
| 1. Monitor Pipe pane输出 | 最近5轮的ALERT/AI_REVIEW/queue/throughput | tmux capture-pane |
| 2. alerts集合 | 所有新alert的详情 | monitor_pipe.py --check-alerts |
| 3. 进程状态 | 5个pipe服务 + monitor_pipe + harness-p/dbmon数 | tmux has-session + pgrep |
| 4. 进度 | Redis队列 + 最近5分钟吞吐 | redis_queue + ArangoDB |
| 5. 系统深度审查结果 | alert按severity/type统计 + 24小时趋势 | ArangoDB pipe_monitor_alerts |

### 3.2 对AI的提醒（核心设计）

每个检查项后附"需要检查"提示，最后一节"系统深度审查结果"是给AI的核心提醒：

```
>> 需要检查（AI核心提醒）：
   ★ 这是Monitor Pipe的系统深度审查结果——AI必须逐项判断每个alert的严重性和处理方案
   ★ critical级别的alert需要立即处理：
     - pipe_service_dead → 检查pipe服务是否崩溃，重启pipe_control.py start
     - session_health critical → runner挂了或feeder没feed，检查对应服务日志
     - rate_limit critical → 立即降并发（pipe_control.py concurrency <更低值>）
     - queue_stalled → 检查collector是否在处理completed队列
   ★ warning级别的alert需要评估是否需要处理：
     - zombie_sessions → 等watchdog清理或手动kill
     - failure_rate → 检查failure_breakdown，判断是AI能力问题还是基础设施问题
     - throughput_drop → 对比历史吞吐，判断是正常波动还是异常
     - solve_time_anomaly → 检查extract_solve_time.py逻辑是否有bug
   ★ info级别的alert是AI review抽样——AI必须检查抽样的proof质量
   ★ 处理完alert后用 monitor_pipe.py --resolve-alert <key> 标记为fixed
   ★ 如果同一类型alert反复出现，说明根因未解决——需要切回系统开发者修复代码
```

## 4. 使用方法

### 4.1 启动（自动包含Monitor Pipe）

```bash
# pipe_start.sh现在自动启动Monitor Pipe
bash xishujuzhen/solver_harness/pipe/pipe_start.sh 20
```

### 4.2 单独启动/停止Monitor Pipe

```bash
# 启动
PYTHONPATH=xishujuzhen/solver_harness/pipe .venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py monitor start --interval 300 --concurrency 20

# 停止
PYTHONPATH=xishujuzhen/solver_harness/pipe .venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py monitor stop

# 查看状态
PYTHONPATH=xishujuzhen/solver_harness/pipe .venv/bin/python3 xishujuzhen/solver_harness/pipe/pipe_control.py monitor status
```

### 4.3 检查

```bash
# 标准化检查（5项+AI提醒）
bash xishujuzhen/solver_harness/pipe/scripts/monitor_check.sh

# 查看新alerts
PYTHONPATH=xishujuzhen/solver_harness/pipe .venv/bin/python3 xishujuzhen/solver_harness/pipe/monitor_pipe.py --check-alerts

# 解决alert
PYTHONPATH=xishujuzhen/solver_harness/pipe .venv/bin/python3 xishujuzhen/solver_harness/pipe/monitor_pipe.py --resolve-alert <alert_key>

# 单轮检查（不循环）
PYTHONPATH=xishujuzhen/solver_harness/pipe .venv/bin/python3 xishujuzhen/solver_harness/pipe/monitor_pipe.py --once
```

### 4.4 停止系统（自动包含Monitor Pipe）

```bash
bash xishujuzhen/solver_harness/pipe/pipe_stop.sh --kill
```

## 7. 后续改进方向

1. **--prompt-file应用到解题系统**：`solver_harness.py`第608行当前用`devin -p '{prompt}'`内联prompt，可改为`devin -p --prompt-file {problem_file}`避免shell转义问题
2. **AI review自动化**：当前AI review抽样标记到DB后需要人工检查，未来可用devin cli + --prompt-file自动检查proof质量
3. **alert自动处理**：当前alert需要人工resolve，未来可对已知问题（如僵尸session）自动处理
4. **并发自动调整**：rate_limit alert触发时自动降并发，throughput_drop时自动升并发
