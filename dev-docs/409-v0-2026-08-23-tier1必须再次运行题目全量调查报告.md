## 1. 调查问题和判定口径

### 1.1 调查问题

用户要求回答：

> tier=1中到底还有多少内容必须由平凡解题系统再次运行解决？

“必须再次运行”不能只等同于“DB最后status不是candidate_solved”。系统目标是采集固定实验条件下的完整`thinking/trajectory/proof`，因此还必须检查：

1. DB中最后run的终态；
2. 硬盘上是否真正留有thinking；
3. proof是否留存；
4. 是否违反“禁止任何工具调用”的实验约束；
5. Redis retry是否覆盖了DB中的基础设施失败；
6. 当前没有pipe-run的题是否已有可复用旧batch资产；
7. 空`problem_text`能否从原始源文件恢复。

### 1.2 四组最终定义

#### valid_completed

满足以下全部条件：

- 至少一个非空thinking来源：
  - `exports/conversation.json.steps[].reasoning_content`；或
  - `sessions_db/trajectory.jsonl[].thinking`；或
  - MITM `content_thinking` / thinking文本；
- 至少一个proof来源：
  - export/trajectory中的`PROOF COMPLETE`；或
  - collector pane中的proof标记；或
  - 旧系统`proof.md`；
- `tool_calls`为空。

#### must_run

满足任一条件：

- 最后终态是基础设施失败；
- 没有终态；
- candidate_solved调用了工具；
- candidate_solved没有thinking；
- candidate_solved没有可核验proof。

#### model_profile

沿用项目AGENTS.md的能力边界：

- `failed_token_limit`
- `ai_gave_up`
- `failed_thinking_spin`
- `failed_tool_stall`
- `failed_no_proof`
- `failed_stall`

这些题在同预算下不要求平凡解题系统再次运行。

#### data_issue

- `answer_leak`
- `answer_leak_in_input`

按当前项目口径不运行。

## 2. 数据源和关键JOIN

### 2.1 数据源

| 数据源 | 位置 | 用途 |
|---|---|---|
| 题库 | ArangoDB `problem_extraction_progress` | tier、题目键、problem_text、external_ref |
| run记录 | ArangoDB `devin_problem_runs` | pipe和旧batch全部终态 |
| 实时队列 | Redis `math:*` | pending/running/failed覆盖情况 |
| trajectory | `/Volumes/data/math-agent-glm5.2-tmux-agents-trajectory/` | export、trajectory、MITM、pane、tmux |
| solver资产 | `/Volumes/data/math-agent-glm5.2-tmux-agents-dir/` | 旧系统problem.txt、proof.md |
| 原始题库 | `/Users/user/glm5.2-math-worktree/knowledge/problem_banks/` | 452道空DB题的源文件 |
| 代码与历史 | 本repo Git历史和pipe代码 | 解释分类、retry和检查器缺陷 |

### 2.2 三种历史键必须同时识别

当前pipe通常使用：

```text
problem_extraction_progress._key = devin_problem_runs.problem_id
```

但452道DB题面为空的题使用数字`_key`，同时还有文本`problem_id`。旧batch可能通过三种方式关联：

```text
r.problem_id == p._key
r.problem_id == p.problem_id
TO_STRING(r.progress_key) == p._key
```

只使用第一种JOIN会把452道已有旧run的题全部误判为“从未运行”。综合脚本对三种键同时建别名。

### 2.3 run选择规则

- pipe：按`ended_at DESC`取每题最后一条非`running`记录；
- 旧batch：
  - 只要存在candidate_solved，审计最后一条candidate资产；
  - 否则排除`running/queued/stopped`后取最后终态；
  - 完全没有终态则归入must_run。
