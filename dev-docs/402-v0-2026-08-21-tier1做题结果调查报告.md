# tier=1 做题结果调查报告

> **调查日期**：2026-08-21
> **数据范围**：`devin_problem_runs`集合，`batch_id=pipe-runner`，tier=1的题
> **调查工具**：`check_retry_effect.py --tier 1`（按每题最后run统计）+ `query_failures.py --by-category`（按所有run统计）

## 0. 关键修正：按每题最后run统计，不是按所有run统计

### 0.1 问题

第一次调查时按`devin_problem_runs`的所有run记录统计，把rate_limited算作5,847题（33.5%）。这是**错误的**——rate_limited是基础设施失败，retry服务会把这些题重新入队，同一道题会有多次run。按所有run统计会把中间run也算进来，严重高估基础设施失败的占比。

### 0.2 正确方法

按**每道题的最后一次run的status**统计。这才是"AI经过运行后最终没有解决的问题"。

### 0.3 验证：retry确实在工作

5,680题经历过基础设施失败（第一次run是rate_limited/dead_session等），重试后的最终结局：

| 最终结局 | 数量 | 占比 |
|---|---|---|
| candidate_solved | 4,359 | 76.7% |
| failed_token_limit | 1,030 | 18.1% |
| crash_recovered | 102 | 1.8% |
| dead_session | 94 | 1.7% |
| rate_limited | 46 | 0.8% |
| 其他 | 49 | 0.9% |

**76.7%的infra失败题重试后成功了**。retry服务有效工作。

### 0.4 两种统计的差异

| 指标 | 按所有run（错误） | 按最后run（正确） |
|---|---|---|
| 总数 | 43,875 run | 37,266 题 |
| 已解决 | 26,397 (60.2%) | 26,314 (70.6%) |
| rate_limited | 5,847 | 46 |
| dead_session | 760 | 96 |

按所有run统计时rate_limited有5,847条，但其中5,801条是中间run——这些题后来被retry重新入队并有了新的终态。按每题最后run统计，rate_limited只剩46题。

## 1. 调查方法

### 1.1 目标

查询tier=1的做题结果，统计多少题AI经过运行后最终没有解决，并按失败原因分类。

### 1.2 数据来源

- **题库**：ArangoDB `problem_extraction_progress`集合（`difficulty_tier=1`的题）
- **运行记录**：ArangoDB `devin_problem_runs`集合（`batch_id=pipe-runner`的run）
- **JOIN关系**：`problem_extraction_progress._key` = `devin_problem_runs.problem_id`

> **关键陷阱**：`devin_problem_runs`中pipe-runner batch的run，`difficulty_tier`字段是`null`。不能直接按`difficulty_tier`过滤`devin_problem_runs`来查tier=1的题，必须JOIN `problem_extraction_progress`。

> **关键陷阱2**：同一道题可能有多次run（retry服务重新入队）。必须按每题**最后一次run**的status统计，不能按所有run统计，否则会把已重试成功的中间run也算成失败。

### 1.3 查询工具

```bash
set -a; source /Users/user/glm5.2-math-worktree/.env; set +a
PYTHONPATH=xishujuzhen/solver_harness/pipe \
  /Users/user/glm5.2-math-worktree/.venv/bin/python3 \
  xishujuzhen/solver_harness/pipe/scripts/check_retry_effect.py --tier 1
```

### 1.4 分类标准

| 分类 | 含义 | 包含的status |
|---|---|---|
| **已解决** | AI输出`### PROOF COMPLETE` | `candidate_solved` |
| **AI能力失败** | 模型做不出，是Profile数据，不重试 | `failed_token_limit` / `ai_gave_up` / `failed_thinking_spin` / `failed_tool_stall` / `failed_no_proof` / `failed_stall` |
| **基础设施失败** | 可重试，不代表AI能力 | `rate_limited` / `dead_session` / `crash_recovered` / `failed_connection` / `launch_error` |
| **数据问题** | 题目本身有问题 | `answer_leak_in_input` / `answer_leak` |

> 分类依据见`解题系统审计方法.md` §2.2 和 `SolverOpsSOP.md` SOP G3。

### 1.5 AQL查询逻辑（按每题最后run）

```aql
FOR p IN problem_extraction_progress
  FILTER p.difficulty_tier == 1
  FOR r IN devin_problem_runs
    FILTER r.problem_id == p._key
    FILTER r.batch_id == "pipe-runner"
    FILTER r.status != "running"
    SORT r.problem_id, r.ended_at DESC
    COLLECT problem_id = r.problem_id INTO runs = r.status
    LET last_status = runs[0]   // ended_at DESC后第一个就是最后一次run
    COLLECT status = last_status WITH COUNT INTO c
    SORT c DESC
    RETURN {status, count: c}
```

## 3. 关键发现

### 3.1 真实解决率70.6%，不是60.2%

按每题最后run统计，tier=1的解决率是70.6%（26,314/37,266），远高于按所有run统计的60.2%。差异来自5,801条rate_limited中间run——这些题后来被retry重新入队并最终解决。

### 3.2 token_limit是绝对主要瓶颈

未解决的10,952题中，9,336题（85.2%）是token_limit。剔除数据问题和残留基础设施失败后，AI能力失败占未解决的91.9%。GLM-5.2在tier=1题上的能力边界几乎完全由token预算决定——AI有思路但推理链太长被截断。

### 3.3 retry服务有效工作

5,680题经历过基础设施失败，其中76.7%重试后成功。retry服务把rate_limited从5,847条降到46条，效果显著。残留的244题基础设施失败是重试3次后仍未成功的。

### 3.4 数据问题很少

639题（5.8%），题库质量基本OK。

### 3.5 真正需要关注的AI能力失败

剔除基础设施失败（244题，retry已尽力）和数据问题（639题，题目本身有问题）后，真正的AI能力失败是10,069题。其中：
- 9,336题（92.8%）是token_limit — 需要分析这些题的特征，判断是题太难还是token预算不够
- 498题（4.9%）是AI主动放弃 — 需要分析AI为什么认为自己解不了
- 235题（2.3%）是卡住/无proof/thinking空转 — 边缘case

## 4. 后续建议

1. **token_limit题的深度分析**：9,336题因token_limit失败，需要抽样分析这些题的特征（题目长度、题型、推理链长度），判断是题太难还是token预算不够
2. **ai_gave_up题的分析**：498题AI主动放弃，分析AI在什么情况下认为自己解不了
3. **跨tier对比**：用`--tier 2`和`--tier 3`运行同样的查询，对比不同难度tier的失败模式差异
4. **残留基础设施失败的排查**：244题重试3次后仍失败，排查是否有系统性问题（如某些时段API不稳定）
