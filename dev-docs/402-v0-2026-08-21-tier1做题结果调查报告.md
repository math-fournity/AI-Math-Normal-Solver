# tier=1 做题结果调查报告

> **调查日期**：2026-08-21
> **数据范围**：`devin_problem_runs`集合，`batch_id=pipe-runner`，tier=1的题
> **调查工具**：`query_failures.py --by-category --tier 1`

---

## 1. 调查方法

### 1.1 目标

查询tier=1的做题结果，统计多少题因为各种原因没有被AI解决，并按失败原因分类。

### 1.2 数据来源

- **题库**：ArangoDB `problem_extraction_progress`集合（`difficulty_tier=1`的题）
- **运行记录**：ArangoDB `devin_problem_runs`集合（`batch_id=pipe-runner`的run）
- **JOIN关系**：`problem_extraction_progress._key` = `devin_problem_runs.problem_id`

> **关键陷阱**：`devin_problem_runs`中pipe-runner batch的run，`difficulty_tier`字段是`null`。不能直接按`difficulty_tier`过滤`devin_problem_runs`来查tier=1的题，必须JOIN `problem_extraction_progress`。

### 1.3 查询工具

使用 `query_failures.py --by-category` 命令：

```bash
set -a; source /Users/user/glm5.2-math-worktree/.env; set +a
PYTHONPATH=xishujuzhen/solver_harness/pipe \
  /Users/user/glm5.2-math-worktree/.venv/bin/python3 \
  xishujuzhen/solver_harness/pipe/query_failures.py --by-category --tier 1
```

参数说明：
- `--by-category`：按三大类分类统计（AI能力失败/基础设施失败/数据问题）
- `--tier 1`：只统计tier=1的题（不指定则统计所有tier）
- `--batch-id pipe-runner`：只统计pipe-runner batch的run（默认值）

### 1.4 分类标准

所有非`running`的run按终态`status`分为四大类：

| 分类 | 含义 | 包含的status |
|---|---|---|
| **已解决** | AI输出`### PROOF COMPLETE` | `candidate_solved` |
| **AI能力失败** | 模型做不出，是Profile数据，不重试 | `failed_token_limit` / `ai_gave_up` / `failed_thinking_spin` / `failed_tool_stall` / `failed_no_proof` / `failed_stall` |
| **基础设施失败** | 可重试，不代表AI能力 | `rate_limited` / `dead_session` / `crash_recovered` / `failed_connection` / `launch_error` |
| **数据问题** | 题目本身有问题 | `answer_leak_in_input` / `answer_leak` |

> 分类依据见`解题系统审计方法.md` §2.2 和 `SolverOpsSOP.md` SOP G3。

### 1.5 AQL查询逻辑

```aql
FOR p IN problem_extraction_progress
  FILTER p.difficulty_tier == 1
  FOR r IN devin_problem_runs
    FILTER r.problem_id == p._key
    FILTER r.batch_id == "pipe-runner"
    FILTER r.status != "running"
    COLLECT status = r.status WITH COUNT INTO c
    SORT c DESC
    RETURN {status, count: c}
```

先按status聚合得到每个status的计数，再在Python侧按三大类分类汇总。

## 3. 关键发现

### 3.1 token_limit是最大瓶颈

9,370题（占未解决的53.6%）因为token用完没做完。这是GLM-5.2在tier=1题上的主要能力边界——AI有思路但推理链太长被截断。

### 3.2 rate_limited占比很高

5,847题（33.5%）因API限流失败。这是基础设施问题，retry服务会重试，但rate limit风暴期间重试也可能再次失败。这部分失败**不代表AI能力**，重试后有可能解决。

### 3.3 真正的AI能力失败

剔除基础设施失败和数据问题后，真正的AI能力失败是10,119题。其中绝大部分（9,370题）是token_limit，说明AI有思路但推理链太长。只有499题（2.9%）是AI主动放弃。

### 3.4 数据问题很少

仅648题（3.7%），题库质量基本OK。

### 3.5 修正后的真实解决率

如果剔除基础设施失败（可重试）和数据问题（题目本身有问题），只看AI能力相关的题：

- AI能力相关题数 = 已解决 + AI能力失败 = 26,397 + 10,119 = 36,516
- 真实解决率 = 26,397 / 36,516 = **72.3%**

这个数字更能反映GLM-5.2在tier=1题上的真实能力边界。

## 4. 后续建议

1. **token_limit题的深度分析**：9,370题因token_limit失败，需要抽样分析这些题的特征（题目长度、题型、推理链长度），判断是题太难还是token预算不够
2. **rate_limited题的重试**：5,847题因rate_limited失败，重启系统后retry服务会自动重试这些题
3. **跨tier对比**：用`--tier 2`和`--tier 3`运行同样的查询，对比不同难度tier的失败模式差异
4. **时间趋势分析**：按`ended_at`时间分段统计，看失败率是否随时间改善（模型更新/系统优化效果）
