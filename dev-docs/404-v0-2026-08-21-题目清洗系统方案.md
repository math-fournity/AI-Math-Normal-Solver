# 题目清洗系统方案

> **创建日期**：2026-08-21
> **目标**：用AI清洗答案泄漏的题目——从包含答案的problem_text中提取出纯净的题目和答案，经验证后更新数据库。原始数据保留到original字段。
> **背景**：tier=1中有639题存在答案泄漏（451题answer_leak_in_input + 188题answer_leak），这些题的problem_text包含了answer/solution内容，不能直接用于解题。详见 `dev-docs/402-v0-2026-08-21-tier1做题结果调查报告.md` 和 `tmp-scripts/analyze_answer_leak.py` 的调查。

---

## 1. 问题分析

### 1.1 答案泄漏的两种类型

| 类型 | 数量 | 泄漏模式 | 数据来源 |
|---|---|---|---|
| answer_in_text | 436 | answer值嵌在problem_text末尾的数学表达式中（位置89%-97%） | deepmath_103k(238) + oda_math_460k(188) + 其他 |
| solution_in_text | 15 | problem_text开头就是solution_text内容（字段搞反） | polymath(22) |
| answer_leak（AI运行中检测） | 188 | AI在解题过程中检测到答案泄漏 | formal_conjectures(135) + 其他 |

### 1.2 为什么不能自动清理

- answer_in_text：answer值是数学表达式的一部分（如`2^\omega \cdot \kappa`），嵌在题目文本的数学表达式中，自动删除会破坏题目结构
- solution_in_text：problem_text和solution_text字段搞反，需要判断哪个是题目哪个是解答
- answer_leak：AI运行中检测到的泄漏，problem_text本身可能没有明显的答案，但AI在推理中发现了答案线索——需要AI来判断

### 1.3 为什么用AI清洗

AI擅长理解自然语言和数学表达式的语义，可以：
- 区分题目中的"答案作为题目的一部分"和"答案泄漏"
- 从混合文本中提取出纯净的题目和答案
- 处理字段搞反的情况
- 判断AI运行中检测到的泄漏是否真的存在

## 2. 三阶段流程设计

### 2.1 总体流程

```
阶段1：AI提取              阶段2：脚本提取结果        阶段3：AI验证
devin -p (清洗prompt)      从阶段1的export中          devin -p (验证prompt)
→ thinking分析             提取XML标签内容            → thinking分析
→ TUI输出XML标签           → 生成中间结果JSON         → TUI输出JSON验证结果
→ export保存                                          → export保存
（无工具调用）                                         （无工具调用）

                          脚本从阶段3的export中提取JSON
                          → question-right & answer-right 都为true → 入库
                          → 任一为false → 标记needs_review → Master Agent人工检查
```

**关键约束**：阶段1和阶段3都是`devin -p`启动新的AI session，**无工具调用，只有thinking分析+TUI输出**。AI不写文件、不执行命令、不搜索、不浏览网页。所有分析在thinking中完成，结果直接输出到TUI，通过export保存到conversation.json供脚本提取。

### 2.2 阶段1：AI提取

用非交互模式（`devin -p`）启动新的AI session，给它清洗prompt。AI在thinking中分析文本，在TUI中输出用XML标签包裹的题目和答案。export保存后供阶段2提取。

**清洗prompt（写入AGENTS.md）**：

```markdown
# Cleaning Task

以下是原始文本，可能包含题目和答案混合的内容：

{problem_text}

## 清洗约束（必须严格遵守）

1. **不要使用任何工具**——不要写文件、不要执行命令、不要搜索、不要浏览网页。
   你只需要在TUI中用thinking来分析文本。

2. **从上面的文本中提取出纯净的题目和答案**：
   - 题目部分：去除答案/solution后的纯题目文本
   - 答案部分：从文本中提取出的答案

3. **直接在TUI中输出提取结果**，用XML标签包裹（内容保持原文语言）：

   <extracted-problem>
   [纯净的题目文本]
   </extracted-problem>

   <extracted-answer>
   [提取出的答案]
   </extracted-answer>

4. **如果无法提取**（文本不是题目、无法区分题目和答案等），输出：

   <extraction-failed>
   [说明为什么无法提取]
   </extraction-failed>

以上是全部约束。现在请提取。
```

**collector判定标记**：

| 标记 | 含义 |
|---|---|
| `<extracted-problem>` + `<extracted-answer>` | 提取成功 |
| `<extraction-failed>` | 提取失败 |

### 2.3 阶段2：脚本提取结果

阶段1的devin cli结束后，脚本从`conversation.json`中提取XML标签内容。

**提取逻辑**：

```python
import re

def extract_from_conversation(conversation_json):
    """从conversation.json中提取XML标签内容"""
    # 合并所有assistant输出
    text = ""
    for step in conversation_json.get("steps", []):
        if step.get("role") == "assistant":
            text += step.get("content", "") + "\n"

    # 提取<extracted-problem>...</extracted-problem>
    problem_match = re.search(r'<extracted-problem>\s*(.*?)\s*</extracted-problem>', text, re.DOTALL)
    # 提取<extracted-answer>...</extracted-answer>
    answer_match = re.search(r'<extracted-answer>\s*(.*?)\s*</extracted-answer>', text, re.DOTALL)
    # 提取<extraction-failed>...</extraction-failed>
    failed_match = re.search(r'<extraction-failed>\s*(.*?)\s*</extraction-failed>', text, re.DOTALL)

    if failed_match:
        return {"status": "failed", "reason": failed_match.group(1).strip()}
    if problem_match and answer_match:
        return {
            "status": "extracted",
            "problem": problem_match.group(1).strip(),
            "answer": answer_match.group(1).strip(),
        }
    return {"status": "parse_error", "raw": text[-500:]}
```

提取结果存入中间文件，供阶段3使用：

```json
{
    "problem_key": "deepmath_103k_00001774",
    "stage1_exp_id": "clean-xxx",
    "original_problem_text": "原始题目文本...",
    "original_answer": "原始答案...",
    "extracted_problem": "提取的题目...",
    "extracted_answer": "提取的答案...",
    "extraction_status": "extracted"
}
```

### 2.4 阶段3：AI验证

用非交互模式（`devin -p`）启动新的AI session，给它验证prompt。AI在thinking中对比原始文本和提取结果，在TUI中输出JSON格式的验证结果。export保存后供脚本提取。

**验证prompt（写入AGENTS.md）**：

```markdown
# Verification Task

以下是原始文本和提取结果，请判断提取是否正确。

## 原始文本
{original_problem_text}

## 提取的题目
{extracted_problem}

## 提取的答案
{extracted_answer}

## 验证约束（必须严格遵守）

1. **不要使用任何工具**——不要写文件、不要执行命令、不要搜索。
   你只需要在TUI中用thinking来分析。

2. **判断提取的题目和答案是否正确**：
   - 题目是否完整、是否去除了答案部分、是否保留了题目的全部信息
   - 答案是否准确、是否是原始文本中的答案

3. **直接在TUI中输出验证结果**，必须是合法的JSON格式：

   {
     "question-right": true或false,
     "answer-right": true或false,
     "question-detail": "如果题目不正确，说明为什么；如果正确，留空",
     "answer-detail": "如果答案不正确，说明为什么；如果正确，留空"
   }

以上是全部约束。现在请验证。
```

**collector判定**：检测AI输出中是否包含合法的JSON（含`question-right`和`answer-right`字段）。

### 2.5 阶段3后的脚本处理

脚本从`conversation.json`中提取AI输出的JSON，根据验证结果决定下一步：

```python
def process_verification(verification_json, extraction_result):
    """根据验证结果决定下一步"""
    q_right = verification_json.get("question-right", False)
    a_right = verification_json.get("answer-right", False)

    if q_right and a_right:
        # 验证通过 → 入库
        update_database(extraction_result)
        return "verified"
    else:
        # 验证不通过 → 标记为需要Master Agent人工检查
        flag_for_manual_review(extraction_result, verification_json)
        return "needs_review"
```

### 2.6 数据库更新（验证通过时）

```python
{
    "_key": problem_key,
    "problem_text": extracted_problem,          # AI提取的纯净题目
    "answer": extracted_answer,                 # AI提取的答案
    "original_problem_text": old_problem_text,  # 原始problem_text（保留）
    "original_answer": old_answer,              # 原始answer（保留）
    "cleaning_status": "verified",              # 清洗+验证完成
    "cleaning_stage1_exp_id": stage1_exp_id,    # 阶段1的exp_id
    "cleaning_stage3_exp_id": stage3_exp_id,    # 阶段3的exp_id
    "cleaning_at": timestamp,                   # 清洗时间
}
```

### 2.7 验证不通过时

标记为`needs_review`，Master Agent亲自检查：

```python
{
    "_key": problem_key,
    "cleaning_status": "needs_review",          # 需要人工检查
    "cleaning_stage1_exp_id": stage1_exp_id,
    "cleaning_stage3_exp_id": stage3_exp_id,
    "cleaning_review_reason": "AI验证不通过",
    "cleaning_review_detail": verification_json,  # AI的验证详情
}
```

Master Agent查看`question-detail`和`answer-detail`，决定：
- 手动修正提取结果后入库
- 重新运行阶段1（换一个AI session重试提取）
- 标记为永久排除（题目本身有问题）

## 3. 实现方案

### 3.1 代码结构

新建 `xishujuzhen/solver_harness/cleaning_pipe/` 目录：

| 文件 | 用途 |
|---|---|
| `cleaning_feeder.py` | 从ArangoDB取答案泄漏的题入Redis队列 |
| `cleaning_runner.py` | 启动devin cli，用清洗prompt（阶段1） |
| `cleaning_collector.py` | 检测XML标记，判定阶段1终态 |
| `cleaning_extract.py` | 阶段2：从conversation.json提取XML内容 |
| `cleaning_verifier_runner.py` | 启动devin cli，用验证prompt（阶段3） |
| `cleaning_verifier_collector.py` | 检测JSON输出，判定阶段3终态 |
| `cleaning_postprocess.py` | 阶段3后：检查JSON，验证通过则入库，不通过则标记needs_review |
| `cleaning_start.sh` | 启动清洗pipe系统 |
| `cleaning_stop.sh` | 停止清洗pipe系统 |

### 3.2 三阶段的数据流

```
ArangoDB (answer_leak题)
    ↓
cleaning_feeder → Redis cleaning:pending
    ↓
【阶段1】cleaning_runner → devin -p (清洗prompt)
    ↓                    输出 <extracted-problem>...</extracted-problem>
    ↓                              <extracted-answer>...</extracted-answer>
cleaning_collector → 检测XML标记
    ↓
【阶段2】cleaning_extract → 从conversation.json提取XML内容
    ↓                    生成中间结果JSON文件
    ↓
【阶段3】cleaning_verifier_runner → devin -p (验证prompt)
    ↓                           输出 {"question-right": true, "answer-right": false, ...}
cleaning_verifier_collector → 检测JSON输出
    ↓
cleaning_postprocess → 检查JSON
    ├── question-right=true & answer-right=true → 更新ArangoDB（original字段+新数据）
    └── question-right=false 或 answer-right=false → 标记needs_review → Master Agent人工检查
```

### 3.3 Redis队列

| 键 | 类型 | 用途 |
|---|---|---|
| `math:cleaning:pending` | sorted set | 待清洗队列（阶段1） |
| `math:cleaning:running` | hash | 正在清洗的run |
| `math:cleaning:completed` | list | 阶段1提取完成，待阶段2提取 |
| `math:cleaning:verify:pending` | sorted set | 待验证队列（阶段3） |
| `math:cleaning:verify:running` | hash | 正在验证的run |
| `math:cleaning:failed` | list | 清洗失败 |

### 3.4 trajectory数据存放

```
/Volumes/data/math-agent-glm5.2-tmux-agents-trajectory/_pipe/cleaning/<exp_id>/
├── exports/conversation.json    # AI的输出（阶段1或阶段3）
├── collector/pane_snapshot.txt  # TUI快照
└── tmux/tmux_pipe.log           # tmux日志
```

exp_id前缀：
- 阶段1：`clean-ext-<problem_key>`（extract）
- 阶段3：`clean-vrf-<problem_key>`（verify）

### 3.5 中间结果文件

阶段2提取后，中间结果存放在：

```
/Volumes/data/math-agent-glm5.2-tmux-agents-trajectory/_pipe/cleaning/results/<problem_key>.json
```

内容见§2.3的中间结果JSON格式。阶段3的验证prompt从这个文件读取提取结果，阶段3后的postprocess也从这个文件读取并更新。

## 5. 注意事项

### 5.1 原始数据保留

清洗后的题在数据库中保留原始数据：
- `original_problem_text`：原始problem_text（含答案）
- `original_answer`：原始answer
- 如果清洗结果有问题，可以用原始数据回滚

### 5.2 清洗后的题重新入队

清洗成功且验证通过的题（`cleaning_status=verified`）可以重新进入解题系统：
- feeder选题时可以加`FILTER p.cleaning_status == "verified"`来优先选清洗过的题
- 或者手动把清洗成功的题入队到`math:pending`

### 5.3 needs_review的处理

验证不通过的题（`cleaning_status=needs_review`）需要Master Agent人工检查：
- 查看`question-detail`和`answer-detail`了解AI认为哪里不正确
- 查看阶段1的conversation.json了解AI提取了什么
- 查看阶段3的conversation.json了解AI为什么认为不正确
- 决定：手动修正 / 重新运行阶段1 / 永久排除

### 5.4 与解题系统的隔离

清洗系统和解题系统可以同时运行：
- Redis队列独立（`math:cleaning:*` vs `math:*`）
- tmux session名独立（`cleaning-*` vs `pipe-*`）
- trajectory目录独立
- 但要注意devin cli的并发总量——两个系统同时运行时总并发不要超过API限制

### 5.5 三阶段的并发控制

- 阶段1和阶段3都是devin -p，消耗API额度
- 阶段2是纯脚本处理，不消耗API
- 阶段1和阶段3可以流水线运行：阶段1完成→阶段2提取→阶段3启动，不需要等所有题阶段1完成再开始阶段3
