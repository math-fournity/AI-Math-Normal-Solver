# 题目清洗系统方案

> **创建日期**：2026-08-21
> **目标**：用AI清洗答案泄漏的题目——从包含答案的problem_text中提取出纯净的题目和答案，更新数据库。原始数据保留到original字段。
> **背景**：tier=1中有639题存在答案泄漏（451题answer_leak_in_input + 188题answer_leak），这些题的problem_text包含了answer/solution内容，不能直接用于解题。详见 `dev-docs/402-v0-2026-08-21-tier1做题结果调查报告.md` 和 `tmp-scripts/analyze_answer_leak.py` 的调查。

---

## 1. 问题分析

### 1.1 答案泄漏的两种类型

| 类型 | 数量 | 泄漏模式 | 数据来源 |
|---|---|---|---|
| answer_in_text | 436 | answer值嵌在problem_text末尾的数学表达式中（位置89%-97%） | deepmath_103k(238) + oda_math_460k(188) + 其他 |
| solution_in_text | 15 | problem_text开头就是solution_text内容（字段搞反） | polymath(22) |
| answer_leak（AI运行中检测） | 188 | AI在解题过程中检测到答案泄漏 | formal_conjectures(135) + 其他 |

### 1.2 为什么不能自动清理

- answer_in_text：answer值是数学表达式的一部分（如`2^\omega \cdot \kappa`），嵌在题目文本的数学表达式中，自动删除会破坏题目结构
- solution_in_text：problem_text和solution_text字段搞反，需要判断哪个是题目哪个是解答
- answer_leak：AI运行中检测到的泄漏，problem_text本身可能没有明显的答案，但AI在推理中发现了答案线索——需要AI来判断

### 1.3 为什么用AI清洗

AI擅长理解自然语言和数学表达式的语义，可以：
- 区分题目中的"答案作为题目的一部分"和"答案泄漏"
- 从混合文本中提取出纯净的题目和答案
- 处理字段搞反的情况
- 判断AI运行中检测到的泄漏是否真的存在

## 2. 方案设计

### 2.1 总体思路

复用平凡解题系统的pipe架构（feeder/runner/collector），但任务从"解题"改为"清洗"：

1. **feeder**：从ArangoDB取答案泄漏的题，入Redis pending队列
2. **runner**：启动devin cli，给AI一个清洗prompt（不是解题prompt）
3. **collector**：检测AI输出中的`### EXTRACTED PROBLEM`和`### EXTRACTED ANSWER`标记
4. **后处理**：从export的conversation.json中提取出AI输出的题目和答案，更新数据库

### 2.2 清洗prompt

AI收到的AGENTS.md内容（注意：不是解题，是提取）：

```markdown
# Cleaning Task

以下是原始文本，可能包含题目和答案混合的内容：

{problem_text}

## 清洗约束（必须严格遵守）

1. **不要使用任何工具**——不要写文件、不要执行命令、不要搜索、不要浏览网页。
   你只需要在TUI中用thinking来分析文本。

2. **从上面的文本中提取出纯净的题目和答案**：
   - 题目部分：去除答案/solution后的纯题目文本
   - 答案部分：从文本中提取出的答案

3. **直接在TUI中输出提取结果**，格式如下（必须用英文标记，内容保持原文语言）：

   ### EXTRACTED PROBLEM
   [纯净的题目文本]

   ### EXTRACTED ANSWER
   [提取出的答案]

4. **如果无法提取**（文本不是题目、无法区分题目和答案等），直接说：

   ### EXTRACTION FAILED

以上是全部约束。现在请提取。
```

### 2.3 输出标记

| 标记 | 含义 | 对应解题系统的标记 |
|---|---|---|
| `### EXTRACTED PROBLEM` | 题目提取完成 | `### PROOF COMPLETE` |
| `### EXTRACTED ANSWER` | 答案提取完成 | （无对应） |
| `### EXTRACTION FAILED` | 提取失败 | `### I CANNOT SOLVE THIS` |

### 2.4 数据库更新

清洗成功后，更新`problem_extraction_progress`集合：

```python
{
    "_key": problem_key,
    "problem_text": extracted_problem,      # AI提取的纯净题目
    "answer": extracted_answer,             # AI提取的答案
    "original_problem_text": old_problem_text,  # 原始problem_text（保留）
    "original_answer": old_answer,          # 原始answer（保留）
    "cleaning_status": "cleaned",           # 清洗状态
    "cleaning_exp_id": exp_id,              # 清洗run的exp_id
    "cleaning_at": timestamp,               # 清洗时间
}
```

> **原始数据不删除**：原始的problem_text和answer移到`original_problem_text`和`original_answer`字段。如果清洗结果有问题，可以回滚。

### 2.5 新的status值

| status | 含义 | 对应解题系统的status |
|---|---|---|
| `cleaned_solved` | AI成功提取出题目和答案 | `candidate_solved` |
| `cleaned_failed` | AI无法提取（EXTRACTION FAILED） | `ai_gave_up` |
| `cleaned_token_limit` | token用完没提取完 | `failed_token_limit` |
| `cleaned_rate_limited` | API限流 | `rate_limited` |

## 3. 实现方案

### 3.1 代码结构

两种实现方式：

**方式A：独立清洗pipe系统（推荐）**

新建 `xishujuzhen/solver_harness/cleaning_pipe/` 目录，包含：
- `cleaning_feeder.py` — 从ArangoDB取答案泄漏的题入队
- `cleaning_runner.py` — 启动devin cli，用清洗prompt
- `cleaning_collector.py` — 检测EXTRACTED标记，提取结果，更新数据库
- `cleaning_postprocess.py` — 从conversation.json提取题目和答案，更新数据库

**方式B：在现有pipe系统中加模式切换**

给runner/collector加一个`--mode cleaning`参数，切换prompt和判定逻辑。

推荐方式A，因为清洗和解题的逻辑差异大（prompt不同、判定标记不同、后处理不同），混在一起会增加复杂度。

### 3.2 关键改造点

#### runner.py → cleaning_runner.py

- `write_problem_file`改为`write_cleaning_task_file`：写入清洗prompt而非解题prompt
- Redis队列用不同的key前缀（如`math:cleaning:pending`），避免和解题队列冲突
- batch_id用`pipe-cleaning`，和解题的`pipe-runner`区分

#### collector.py → cleaning_collector.py

- 判定标记从`PROOF COMPLETE`改为`EXTRACTED PROBLEM` + `EXTRACTED ANSWER`
- 新增`has_extraction(detect_text)`函数：检测AI是否输出了完整的提取结果
- 不需要检测`ANSWER LEAK DETECTED`（清洗任务中AI就是要处理答案）

#### 后处理（新增）

- 从`conversation.json`的`steps`中提取AI的assistant输出
- 解析`### EXTRACTED PROBLEM`和`### EXTRACTED ANSWER`之间的内容
- 更新ArangoDB：原始数据移到original字段，新数据放回主字段

### 3.3 数据流

```
ArangoDB (answer_leak题) → cleaning_feeder → Redis cleaning:pending
                                              ↓
                                        cleaning_runner → 启动devin cli (清洗prompt)
                                              ↓
                                        Redis cleaning:running
                                              ↓
                                        cleaning_collector → 检测EXTRACTED标记
                                              ↓
                                        cleaning_postprocess → 从conversation.json提取
                                              ↓
                                        更新ArangoDB (original字段 + 新数据)
                                              ↓
                                        清洗后的题可重新进入解题系统
```

### 3.4 Redis队列

| 键 | 类型 | 用途 |
|---|---|---|
| `math:cleaning:pending` | sorted set | 待清洗队列 |
| `math:cleaning:running` | hash | 正在清洗的run |
| `math:cleaning:completed` | list | 清洗完成 |
| `math:cleaning:failed` | list | 清洗失败 |

与解题系统的`math:pending`等队列完全独立，互不干扰。

### 3.5 trajectory数据存放

清洗run的trajectory数据存放在独立目录：

```
/Volumes/data/math-agent-glm5.2-tmux-agents-trajectory/_pipe/cleaning/<exp_id>/
├── exports/conversation.json    # AI的清洗输出
├── collector/pane_snapshot.txt  # TUI快照
└── tmux/tmux_pipe.log           # tmux日志
```

exp_id前缀用`clean-`，和解题run的exp_id区分。

## 5. 注意事项

### 5.1 原始数据保留

清洗后的题在数据库中保留原始数据：
- `original_problem_text`：原始problem_text（含答案）
- `original_answer`：原始answer
- 如果清洗结果有问题，可以用原始数据回滚

### 5.2 清洗后的题重新入队

清洗成功的题（`cleaning_status=cleaned`）可以重新进入解题系统：
- feeder选题时可以加`FILTER p.cleaning_status == "cleaned"`来优先选清洗过的题
- 或者手动把清洗成功的题入队到`math:pending`

### 5.3 清洗失败的处理

- `cleaned_failed`（AI无法提取）：这些题可能需要人工处理
- `cleaned_token_limit`：可以重试（但清洗任务比解题简单，token_limit应该很少）
- `cleaned_rate_limited`：retry自动重试

### 5.4 与解题系统的隔离

清洗系统和解题系统可以同时运行：
- Redis队列独立（`math:cleaning:*` vs `math:*`）
- tmux session名独立（`cleaning-*` vs `pipe-*`）
- trajectory目录独立
- 但要注意devin cli的并发总量——两个系统同时运行时总并发不要超过API限制
